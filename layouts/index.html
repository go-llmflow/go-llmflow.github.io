LLM serving for a shared GPU cluster,
in pure Go.

go-llmflow is high-performance LLM inference and serving in Go. Its first project, gateway, is an OpenAI-compatible gateway in front of vLLM for clusters that several institutions own together: each team gets its share, and the share a team leaves idle is lent to the others.

The gateway

One OpenAI endpoint, many owners.

The gateway sits between your users' OpenAI clients and the vLLM instances of a cluster. v0.22.1 is the current release: llmflow-gateway has serve, export, check-config and version, and is configured in HCL2 with diagnostics down to file, line and column. Its open limitations (one replica per pool, no TLS) and its roadmap (governance, identity, audit and logging, and guardrails are done) are in the documentation.

🔑

Organisations, teams, keys

The tree of a Slurm account: organisation (institution), team (lab), project, key. Every request is charged to the right share. Keys are stored hashed; roles (proxy, organisation and team admins, members, viewers) delegate the administration through an admin API.

🪪

Your identity provider

OpenID Connect access tokens on the inference API, single sign-on for administrators, SAML federations such as RENATER and eduGAIN through authn-bridge, and SCIM provisioning of users and groups, all on go-authn. Keys can be rotated on a schedule.

📜

An audit log you can check

Every administrative change is recorded in a hash-chained log with signed checkpoints, which can be anchored on write-once S3 or Ceph storage. Per-team request logs keep prompts and answers out unless a team opts in. The documentation states what the log does not protect against.

🤖

For coding agents

Besides chat completions, the gateway serves the OpenAI Responses API (stateless only, so that no tenant can read another's conversation even if vLLM's response store is enabled) and the Anthropic Messages API, so agents that speak it can use the cluster's own models. A model can fall back to a spare one when it is down, or, for a borrowing request, when its pool is saturated (v0.11.0), since a saturated vLLM queues instead of refusing. Since v0.12.0 a model can also be Anthropic's API, opt-in: one API key and workspace per institution, PII and secret guardrails required before a prompt leaves, and costs in USD kept apart from GPU-hours. See the documentation.

🖥️

An admin web UI

Keys, budgets, spend, the live fair-share state and the audit log (with a button that verifies the chain), in pages served with no JavaScript, under a strict content-security policy, behind single sign-on. It has the same roles as the API.

📊

Finance reports

Since v0.13.0 a request names its project in a header, and the report groups by organisation, lab, team, project and user, with the previous period alongside and SVG charts. It exports to CSV, XLSX and PDF (every download audited, spreadsheet-formula injection refused) and sets inference GPU-hours beside Slurm's sreport. GPU-hours and a currency are never added together. What a finance director gets, and what it does not do yet.

🔁

Several replicas

Since v0.14.0 an optional ha block lets several gateway replicas share the pools with PostgreSQL as the only shared component: one owner per pool through a lease with a fencing epoch, and the owner's decision forwarded between replicas. In the chaos tests of 2026-10-26 (PostgreSQL 18), a killed owner was replaced in 1.3 s with no request failed, and a partitioned owner never overlapped the new one. The channel between replicas can run over mutual TLS (use v0.16.1 or later: v0.16.0 refused real certificate files). The latency a forwarded admission adds is not measured yet. High availability.

🗓️

vLLM as Slurm jobs

Since v0.15.0 a model can follow the running Slurm jobs named llmflow:model:port of a service account, admitted once vLLM answers and drained when the job ends, with the pool's capacity recomputed and audited, and nothing admitted from an account or partition that was not configured. Tested on a real Slurm node with a small CPU model: admitted in 18 s, removed 2 s after scancel. Since v0.15.2 it works with several replicas. Slurm discovery, and the deployment overview.

🧰

An MCP gateway

Tool servers for agents behind POST /mcp, with per-team allow-lists that are closed by default. Every call is audited before it is made, with its arguments hashed and never stored, and only the servers in the configuration are ever reached.

📈

Warnings, energy and lending

Since v0.19.0 a person is warned before a window runs out: at 75 % and 95 % by default (configurable per gateway, organisation, profile and user budget), in response headers, at /v1/me/usage, in a Claude Code status line with llmflow-status, and by mail or webhook once per window. The gateway does not emit Anthropic's own ratelimit-unified headers, whose format is not public. Two decision reports come with it: fluids, the electricity each consumer really used, measured from each GPU's DCGM exporter and attributed exactly in millijoules, and lending, the guaranteed share against use, with the GPU-hours borrowed and lent and the admission waits. Decision reports.

🧾

Chargeback and the monthly report

Since v0.20.0 a finance_viewer role, granted by a proxy admin only, reads the reports of every organisation and nothing else. Organisations, labs and projects carry general-ledger cost centres, and a chargeback file gives one row per cost centre and month, with money in exact integer cents (rounded once, half to even) and rows for what has no code, so it always adds up. Adoption counts active people without a name, and suppresses any cell with fewer than five. A monthly decision report, one page per partner in PDF plus an XLSX, is delivered on a schedule to an export and by mail; since v0.21.0 it also sets the energy Slurm accounted for each partner's jobs beside the energy measured on the GPUs, as a question rather than an error, since Slurm's figure is exact only for an exclusive allocation. Since v0.22.0 it also reports soft-quota events and hard refusals, assigned against used workload days, oversubscription over time, and budget against actual with a flag beyond a threshold (15 % by default). It never carries a row per person: a cell needs at least five distinct people, and a hidden figure cannot be recovered by subtracting what is shown, including across the adoption table's days, weeks and models (a gap there, in v0.22.0, was fixed in v0.22.1: some cells v0.22.0 showed are now suppressed). Mail now requires TLS: a relay without STARTTLS fails every send until it is fixed, and the PDF engine adds about 52 % to the binary. The migration note.

🔒

Security fixes in v0.18.1 and v0.18.2

A post-merge review of the workload profiles found two defects in v0.18.0, both fixed in v0.18.1: a rolling window could forget spend when it was widened, so a session budget could be exceeded, and an organisation admin could take over a person by granting them the viewer role. A person now belongs to the teams they are bound to; an organisation role is authority, not membership, so an organisation admin no longer manages another organisation admin who is in no team. Upgrade if you use profiles. v0.18.2 security fix: a residual case, an organisation admin pulling a user who had no binding, or who belonged to another organisation, into their organisation with a team role, is closed. Every role binding now records its provenance (SCIM, SSO claim, proxy admin or org admin), and the first grant to such a user needs a proxy admin. Details.

🗓️

Workload profiles

Since v0.18.0 an administrator, in finance or HR as much as IT, gives each person a profile in days per week (a quarter day to seven), enforced by the hard budgets below. The unit, a workday, is measured from real usage (the 75th percentile of active person-days is proposed, and a proxy admin accepts it), not guessed. A weekly allowance and a rolling five-hour session window stop one sitting from burning the week; overflow is a capped monthly extra, like Anthropic's capped usage credits; organisation and team admins assign the people of their scope. A capacity page shows the oversubscription ratio. The labels are day counts, not Anthropic plan names. Soft quotas and 75 % warnings are not shipped. Workload profiles.

💳

Budgets that are never exceeded

Budgets in GPU-hours (or a currency) per day, week or month on every scope, user included, with soft-limit alerts and temporary increases, and per-key limits on requests, tokens and requests in flight. Since v0.17.0 a request starts only when every budget it falls under can pay its worst case, taken from vLLM's own bound on the output, as Slurm's AccountingStorageEnforce=safe does for a job; grants in PostgreSQL keep spent plus grants within the limit across replicas. A live test against a real vLLM kept usage within that bound in six cases. A budget created mid-period starts arming (v0.17.1): requests in its scope are refused briefly until every gateway process has reported what it still has in flight, and the guarantee is stated as max(limit, the cost of the work admitted before the budget existed). The cost of this check in latency is not measured yet. The guarantee needs the default fail-closed store: with fail_closed = false it is void. Hard budgets.

🔌

OpenAI-compatible

The request is rewritten on the way in, the response, a server-sent-events stream included, is passed through event by event, and token usage is captured for accounting. The parsers are fuzzed.

⚙️

GPU-hour accounting

Usage is counted per team in GPU-hours, the unit of Slurm's sreport, and exported as CSV to reconcile inference with batch. Measured against LiteLLM 1.106.2 over 16,000 paired rounds: 117 µs added at p50 against 4.86 ms, with no streaming, concurrency or database write in the test (protocol and limits).

Fair-share

A guaranteed share, and the idle rest.

Static quotas leave the share of an absent team unused. The gateway reserves each team its share of a pool, and lets the others borrow what is idle. It does so with the one knob vLLM has: the priority of a request.

🎯

Within the share

While an organisation has fewer requests running than its reservation (its share times the pool's capacity), the request gets vLLM priority 0 (interactive) or 1 (batch).

🤝

Borrowing

Above the reservation the request borrows, at priority 10 (interactive) or 11 (batch) and above, the teams that consumed least first (the ranking is Slurm Fair Tree's level fairshare). vLLM admits within-share requests first and preempts borrowers first when KV-cache memory runs out.

🧪

Simulated

A deterministic simulator of vLLM's v1 priority scheduler checks the policy: with both teams saturating, the running fraction follows the shares (0.79 and 0.21 against 0.8125 and 0.1875), and a control with every request at priority 0 does not.

Security

The client never sets its own priority.

A priority a client can choose is a priority every client chooses. The gateway removes priority, extra_body, request_id, kv_transfer_params, ec_transfer_params and vllm_xargs from the request before it reaches vLLM, and decides the priority itself.

🧹

Re-encoded, not patched

The body is re-encoded from its parsed form, so duplicate keys and escaped spellings of a field name cannot reach vLLM. A fuzz target checks that no stripped field survives.

🧊

No shared prefix cache

vLLM's prefix-cache reuse is a timing side channel between tenants (CVE-2025-46570). The gateway sets a stable per-tenant cache_salt, by organisation by default, and drops the client's. Users within one scope can still probe each other, and a salt is not a hard boundary: the documentation says what remains.

🛡️

Audited, then fixed

A security audit and chaos run of v0.8.0 on 2026-10-26 found nine issues (two high, four medium, three low), among them tenant uuids on rerank and embeddings, a client that never reads its answer, and a disabled administrator re-enabled by another organisation's admin. All are fixed in v0.9.0, each with a test that fails without the fix, and the residual risks are written down. Read the audit.

💾

Billing records that survive an outage

Usage is billed between institutions, so since v0.10.0 every batch of records is written to a spool and synced before it goes to PostgreSQL. In the chaos test of 2026-10-26, 21 of 21 records of a PostgreSQL outage were stored once, where v0.9.0 lost all 21. A record still in memory when the process dies is not covered.

📄

Strict configuration

Unknown keys are rejected, upstream URLs are limited to http and https without credentials, and secrets are read from files only, never from the command line.
